Subject: Discovery offer: what we need from the client, and what we deliver

Hi team,

We are leading with a fixed-scope Discovery as the first offer. Below are the pointers to prepare the proposal. The full detail is in docs/offering/06-discovery-offer.md in our private repository, and a working demo is in the Org Compiler.

1. What Discovery is
- A read-only discovery of each of the client's regional Salesforce orgs (our example has 3 orgs and 37 markets), done by our agents and reviewed by our architects.
- It covers what is built on top of standard Salesforce and what is standard, installed packages, business processes and rules, code, security, integrations, usage and technical debt.
- It compares the orgs capability by capability, proposes a fit-gap per component (adopt a standard feature, replace with configuration, keep and harmonise, retire, review in workshop) and a prioritised roadmap.
- Out of scope: design, build and data migration. These follow as separate phases.
- Discovery uses no language model. The agents read Salesforce through its standard APIs, so the results are repeatable and can be re-run after any change.

2. What we need from the client to connect (week 0, before the timeline starts)
- The agreed list of orgs and markets, and for each org the sandbox we connect to. We recommend a Full Copy sandbox refreshed shortly before week 1: same configuration, code and data as production. A Partial Copy works with sample usage figures; a Developer sandbox covers configuration and code only.
- A dedicated read-only integration user per org, with a permission set: API Enabled, View Setup and Configuration, and read access to the objects in scope. No edit rights and no Modify Metadata.
- Credentials for that user, so runs work unattended and do not expire between workshops. Preferred: the JWT bearer flow. The client approves our connected app for the integration user, and we keep the private key in our vault. No password changes hands and nothing expires. Fallback, only where the org's policy allows it: username, password and security token through a secure channel, with "password never expires" set on that user.
- Why not a one-time sign-in: Discovery is re-run over several weeks, and a token from an interactive sign-in ends at the next password reset or admin revocation. We keep "Connect with Salesforce" for demos and pilots.
- Login IP ranges opened for our runner's address, if the org restricts sign-in by IP.
- API capacity: a run uses about 2,000 to 6,000 API calls per org (planned at under 10,000), well within the daily allowance of an Enterprise or Unlimited org.
- Usage evidence that only production holds (login history, report runs, real volumes): either one short read-only pass on production, if the client agrees, or standard Salesforce reports the client exports.
- Agreement on data classification: the outputs hold metadata names, configuration and counts, never record contents.

3. Where the work happens: our git first
- The agents run in a dedicated, access-restricted runner in our environment, with the credentials in our vault.
- Two repositories keep removal clean. The product repository (agents, rules, templates) never holds client material. One engagement repository per client holds only that client's generated artifacts and review records.
- While the engagement repository is ours we use: one commit per run, so changes between runs are visible; review gates as pull requests with recorded decisions; CI that regenerates the outputs and fails if anything differs from what was reviewed; a tag per approved version; and the HTML explorer built from it.
- If the client's policy does not allow credentials or outputs outside its environment, the same setup runs on a VM in their cloud, with the engagement repository in their git from the start.

4. What we deliver
- One Discovery Report covering all orgs. It contains an executive summary; scope and method; a current system landscape diagram; findings by area, each with risk level, business impact, evidence, recommendation and priority; customised versus standard per org; data model diagrams; the fit-gap and cross-org comparison; a prioritised roadmap (quick wins, immediate, medium term, strategic); the target direction; and an appendix per org.
- The appendix for each org has twelve sections: org profile; customised versus standard; data model; validation rules; business processes and automation (process maps and flow diagrams); code inventory; installed packages; security model; integrations; user interface; reports and usage; technical debt.
- Fit-gap data: every custom component with its capability, proposed verdict and reason. After the workshops it becomes the record of the decisions.
- Architecture and principles: the principles we apply, how the Discovery runs, how a verdict is reached, and the target direction.
- The Discovery explorer, an interactive page in the Org Compiler. The client clicks through each org's business processes, validation rules, flows, objects and fields, custom versus standard, packages, security and integrations, in a business view with the raw data one click away.
- A readout session and a workshop agenda covering review items, licence questions and retirement candidates.

5. Timeline and effort, agent-assisted (week 0 depends on the client and comes first)
- Small: week 0 of 1 to 2 weeks, then 3 weeks, 13 person-weeks.
- Medium: week 0 of 2 to 3 weeks, then 4 weeks, 25 person-weeks.
- Large: week 0 of 3 to 4 weeks, then 6 weeks, 56 person-weeks.
- A typical manual discovery for comparison: about 6 to 7, 9 to 10 and 14 to 15 weeks, and about 32, 70 and 150 person-weeks.
- The agents save time on inventory, documentation, the cross-org comparison and re-runs. They do not shorten workshops, business interviews or the client's access lead time. Starting on a sandbox usually shortens week 0.
- Commercials: a fixed price per size, calculated as person-weeks times the blended rate from the Ascendion rate card. All figures are illustrative until the pilot calibrates them.

6. Handover, and removal from our git
- After review, we push the approved artifacts from the engagement repository to the client's git and verify them by commit hash.
- Once the client confirms receipt, we delete the whole engagement repository, not just its files (git keeps deleted files in history). That also removes its pull requests, CI logs and build artifacts. We then purge forks, local clones and runner workspaces.
- We delete the integration user's credentials and private key from our vault. The client deactivates the user and revokes our connected app.
- We send a dated deletion confirmation for the client to countersign.
- Ascendion keeps only the product repository: agent code, rules and templates, never client data.
