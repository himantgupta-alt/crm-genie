# Conventions and patterns

The rules we follow for everything in `src/` and `adlc/`. `src/generators/check-conventions.js` enforces the
checkable ones in CI.

## Layout

- **Outputs by agent.** Every output lives in `adlc/<phase>/<agent>/`, the folder of the agent that produces
  it; each agent spec (`src/agents/<agent>/agent.json`) declares that folder as `outputDir` and lists its
  outputs. `adlc/README.md` and each folder's `README.md` are generated from the specs.
- **Code separate from outputs.** Code that produces or runs outputs is in `src/`: `generators/`, `agents/`,
  `app/`, `verification/`, `console/`, `salesforce-seed/`.
- **One source of paths.** Only `src/paths.js` knows the layout. Nothing else builds a path from string
  fragments like `'output'` or `'target'`; the check rejects the pre-ADLC paths.

## Generated artifacts

- **Deterministic.** The same inputs give byte-identical outputs: no run dates, sorted listings, a content hash
  on the blueprint. CI regenerates the blueprint, SQL, documents and index and fails on any difference.
- **Provenance header.** Every generated file names its owner agent and generator in its first lines
  (`-- Owner: …` and `-- GENERATED by …` in SQL; `Owner: …` in Markdown).
- **Never hand-edited.** To change an output, change its input or its generator and re-run.

## Database (adlc/3-build)

- **Numbered migrations, one owner each.** `000–030` Schema agent, `040–050` Logic agent, `060` Security agent;
  numbers are unique; `adlc/3-build/manifest.json` gives the apply order and pins the blueprint hash.
- **Rebuildable.** Migrations rebuild the schema from the blueprint; rollback is the previous release.
- **Names.** Tables and columns in `snake_case` from the blueprint vocabulary; constraints and triggers named
  after the Salesforce rule they implement.
- **Patterns.** Generated columns for row-local formulas; views for cross-object formulas; trigger-maintained
  roll-ups with a recompute backstop; CHECK constraints and guard triggers for rules; one role per profile or
  permission set, column grants and row-level security. Each pattern has an ADR in
  `adlc/2-design/modelling/design/adr/`.

## Design documents (adlc/2-design/modelling/design)

- **HLD** follows arc42 (goals, constraints, context, solution strategy, building blocks, runtime, deployment,
  cross-cutting concepts, decisions, quality, risks, glossary), with **C4** context and container views.
- **LLD** covers tables, calculated fields, rules, automations with order of execution, services, security,
  load order, migrations, patterns, verification cases and the **traceability matrix**.
- **ADRs** (Nygard format: context, decision, consequences, what it applies to), one per design strategy.
- Diagrams are Mermaid, generated from metadata; they render on GitHub and in the Org Compiler console.

## Code (src)

- Node.js, CommonJS, no build step; small single-purpose scripts with a usage comment at the top.
- Read-only against Salesforce; nothing writes to the org except the seed scripts in `src/salesforce-seed/`.
- No secrets in code or outputs: credentials come from the Salesforce CLI, environment variables or `.secrets/`
  (git-ignored); files that list individual users are git-ignored.
- Tests: `node --test "src/generators/test/*.test.js"`; behaviour is proven by parity (`src/verification/run.js`).

## Agents

- One agent, one job, one output folder, a machine-checkable `done_when`, and reviewer checks for its gate.
- LLM agents (Logic, Repair) write proposals marked for review; nothing they produce merges without approval.
